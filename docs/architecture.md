# Architecture and technical decisions (Phase 1)

> Status: **proposed for owner review.** Entries marked **Owner decision** need a yes/no before Phase 2.

## 1. Components

| Component | Tech (spec §5.1) | Responsibility |
|---|---|---|
| `apps/web` | Next.js 16, React 19, TypeScript, Tailwind 4, Radix, Recharts | Desktop UI. It renders server data and holds no business rules beyond formatting and previews. |
| `apps/mobile` | Expo + React Native + Expo Router | Fast logging and checking progress. Owns the offline pending-action queue. |
| `backend` | Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 (async), Alembic | API, validation, authorization, progression engine, analytics. |
| Database | Managed PostgreSQL 16 | System of record. |
| Object storage | S3-compatible, private bucket | Progress photos only, accessed through short-lived signed URLs. |
| `packages/api-types` | `openapi-typescript` | TypeScript types generated from `docs/api/openapi.yaml`, shared by web and mobile. |

### Backend layout (spec §5.3)

```text
backend/app/
  api/v1/          routers: one file per area (auth, dashboard, academics, fitness, health, productivity, progression, goals, analytics, sync, settings)
  core/            config (env), security (hashing, tokens), errors (problem+json), idempotency middleware, rate limits
  models/          SQLAlchemy models, one module per area
  schemas/         Pydantic request/response models, the same names as the OpenAPI components
  repositories/    queries; every method takes user_id and filters by it
  services/        use-cases; transaction boundaries live here
  progression/     event pipeline, rule evaluation, XP ledger, levels, form, attributes
  analytics/       summaries, trends, correlations (Pandas/NumPy)
  jobs/            scheduled work (nightly attribute snapshots, weekly quest reset, cleanup)
```

**Request flow:**
1. Router validates the input with Pydantic.
2. Service runs in one database transaction:
   - writes the record;
   - emits an `activity_event`;
   - the progression engine evaluates rules and writes `xp_transactions` (same transaction, so exactly once);
   - stores the idempotency record.
3. Commit, then return the response.

## 3. Decision log

| # | Decision | Why | Status |
|---|---|---|---|
| D1 | **UUID primary keys, generated by the client for offline-creatable records** (sessions, sets, daily logs, tasks, habit logs); server-generated otherwise | Offline children (sets) can reference an offline parent (workout) before sync; IDs never collide | Proposed |
| D2 | **`Idempotency-Key` header required on every mutating request**; stored 30 days with a request hash and the response | Exactly-once replays from the offline queue; a reused key with a different body gets `422` | Proposed |
| D3 | **Optimistic concurrency with an integer `version`** (`If-Match`) on editable records; `409` with the server copy on mismatch | Spec §9: "do not silently overwrite server records" | Proposed |
| D4 | **Soft delete (`deleted_at`) plus a global `change_seq`** on synced tables | Lets clients pull deltas and tombstones with one cursor | Proposed |
| D5 | **Store `timestamptz` (UTC) plus `local_date` and the owner's IANA timezone** | Day-based rules (on-plan days, streaks, check-in per day) must follow the owner's local day, not UTC | Proposed |
| D6 | **XP is an append-only ledger** (`xp_transactions`); levels and totals are cached and rebuildable | Auditability; lifetime XP never decreases; corrections are visible entries | Proposed |
| D7 | **XP rules live in versioned `xp_rules` rows**; each transaction records the rule version | Spec §4.2 "configurable and documented"; rule changes apply forward only | Proposed |
| D8 | **Derived metrics computed on read, attributes snapshotted nightly** | Form and trends are cheap over 6–8 weeks of rows; snapshots give attribute history | Proposed |
| D9 | **Web auth: httpOnly cookies. Mobile auth: bearer tokens in SecureStore** | Spec §8 | Proposed |
| D10 | **Errors use RFC 9457 `application/problem+json`** with a stable `code` | One error shape for both clients | Proposed |
| D11 | **Cursor pagination** (`?cursor=…&limit=…`), maximum 200 | Stable under inserts; fits the sync model | Proposed |
| D12 | **Design-first OpenAPI** (`docs/api/openapi.yaml`); a contract test compares it with FastAPI's generated schema | Web and mobile can build against the contract in parallel | Proposed |
| D13 | **Units:** kg, km, minutes, hours as decimals; no unit conversion in v1 | Owner-approved kg; one user | Approved (Phase 0) |
| D14 | **Week starts Monday**; quests reset Monday 00:00 local | Owner-approved | Approved (Phase 0) |
| D15 | **Python 3.12, FastAPI, SQLAlchemy 2 async with asyncpg, Pydantic v2, Alembic, pytest, ruff** | Spec stack; current stable versions at Phase 2 start get pinned in `pyproject.toml` | Proposed |
| D16 | **Monorepo with its own Git repository** at the LifeOs folder | The current Git root is the owner's home folder, so nothing can be committed safely | **Owner decision** |

## 4. Non-goals for v1
- Multiple users, organizations, sharing or public profiles.
- Nutrition or meal tracking (spec principle 7).
- Wearable integrations beyond a manual or CSV import path for steps and resting HR. Which source to support first is an open question.
- Real-time push. Clients refetch on focus and after sync.
